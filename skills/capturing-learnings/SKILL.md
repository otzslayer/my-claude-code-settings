# 학습 기록 (capturing-learnings)

작업에서 배운 것을 `docs/solutions/`에 영구 지식으로 남긴다.

**최종 산출물은 파일 하나이거나 아무것도 아니다.** "학습 없음"은 실패가 아니다. 정상 종료다. 매 실행마다
문서를 뱉는 회고는 코퍼스를 노이즈로 채우고 노이즈가 섞인 코퍼스는 아무도 검색하지 않는다.

**한 실행에 학습 하나.** 중복 확인과 교차 참조가 그것을 전제한다. 한 세션에서 학습이 여럿 나왔으면
스킬을 여러 번 순차로 돌린다.

## 체크리스트

각 항목을 할 일로 만들고 순서대로 처리한다.

1. 게이트 1: 근거 확보 (모드 결정, 또는 중단)
2. 게이트 2: 학습 판정 (또는 "학습 없음"으로 종료)
3. 트랙, `problem_type`, 카테고리 결정
4. 중복 확인 (신규 작성 vs 기존 갱신)
5. 문서 작성
6. 근거 확인 (코드 동작 주장을 트리에서 검증)
7. 커밋

---

## 1. 게이트 1: 근거 확보

| 상황 | 모드 |
|---|---|
| 이 세션에 회고할 작업 맥락이 있다 | **세션 모드** |
| 맥락은 없지만 사용자가 조사 대상을 지정했다 | **브랜치 증거 모드** |
| 맥락도 없고 지정도 없다 | **중단** |

"조사 대상 지정"이란 사용자가 호출과 함께 **주제**("이런 내용으로 학습을 작성해줘") 또는
**범위**("이 브랜치에서 학습할 내용을 찾아 작성해줘")를 준 경우다. 애매하면 `AskUserQuestion`으로 묻는다.

**중단할 때**는 파일을 쓰지 않고 이렇게만 알린다: 이 세션에 작업 맥락이 없다는 사실 + 두 갈래
(작업 세션에서 다시 부르거나 조사 대상을 지정해 다시 부르거나). **맥락이 없다고 조용히 진행하지 않는다.**
근거 없는 문서가 코퍼스에 들어오면 검색 가치가 무너진다.

### 세션 모드

대화 컨텍스트가 1차 증거다. git과 계획 파일은 보조다. 가장 값나가는 재료는 **버려진 접근, 잘못 짚은 원인,
중간에 뒤집힌 판단**이고 이것은 오직 세션에만 있다.

### 브랜치 증거 모드

근거를 이 순서로 모은다:

1. `git log <base>..HEAD` **전체 본문**: 1차 근거. 이 저장소는 커밋 본문에 WHY 불릿을 강제하므로
   여기에 실패 경로가 부분적으로 남는다
2. `git diff <base>...HEAD`: 무엇이 바뀌었나
3. `docs/plans/` 해당 계획 파일: 폐기된 선택지, 계획과 실제의 괴리
4. `docs/superpowers/specs/` 해당 스펙: 설계 결정의 근거
5. `TODO.md`: 범위 밖으로 남긴 것과 그 이유
6. `gh pr view`: PR이 있을 때만
7. 사용자가 준 주제 힌트

`<base>`는 기본 `main`. 다르면 사용자에게 확인한다.

**규칙 둘. 이 모드의 품질은 전적으로 여기에 달려 있다.**

1. **추측으로 서사를 만들지 않는다.** "무엇이 안 통했는가"는 커밋 본문이나 계획 파일에 실제 기록이
   있을 때만 쓴다. 없으면 그 섹션을 **통째로 생략**한다. 빈 섹션도 그럴듯한 재구성도 금지한다.
2. **출처를 본문에 박는다.** 제목 바로 아래 인용 한 줄:
   `> 이 문서는 세션 맥락 없이 브랜치 증거(커밋 본문과 계획 파일)만으로 작성됐다.`

**전제**: 이 모드는 커밋 본문의 WHY 불릿과 `docs/plans/`, `docs/superpowers/specs/`의 설계 기록에 기댄다.
그 규율이 없는 저장소에서는 근거가 얇다. 얇으면 문서를 줄이거나 게이트 2에서 탈락시킨다. 채우려 들지 않는다.

## 2. 게이트 2: 학습 판정

두 모드 공통. **셋 다 "예"여야 문서를 쓴다.**

| 질문 | 탈락하는 것 |
|---|---|
| **(a) 비자명한가** | 오타, 명백한 실수, 공식 문서만 읽어도 아는 것 |
| **(b) 재발하는가** | 이 저장소나 다음 프로젝트에서 다시 겪을 종류인가. 1회성 데이터 정리, 일회성 마이그레이션은 탈락 |
| **(c) 트리 밖 지식인가** | 코드, 커밋, 계획 파일을 읽으면 알 수 있는 것은 탈락. 값어치는 "왜 그렇게 됐는가"와 "무엇이 안 통했는가"에 있다 |

**탈락하면** 이 한 줄만 출력하고 끝낸다: `학습 없음: <어느 질문에서 왜 탈락했는지>`.
파일도 커밋도 없다. 이것이 정상 종료다.

판정을 사용자에게 떠넘기지 않는다. 다만 통과가 아슬아슬하다고 판단되면 근거를 밝히고 물어볼 수 있다.

## 3. 트랙, problem_type, 카테고리

| 트랙 | problem_type | 디렉터리 |
|---|---|---|
| bug | `runtime_error` | `docs/solutions/runtime-errors/` |
| bug | `build_error` | `docs/solutions/build-errors/` |
| bug | `test_failure` | `docs/solutions/test-failures/` |
| knowledge | `design_pattern` | `docs/solutions/design-patterns/` |
| knowledge | `workflow_issue` | `docs/solutions/workflow-issues/` |
| knowledge | `convention` | `docs/solutions/conventions/` |

**bug 트랙**은 무언가가 고장 났고 고쳤을 때 쓴다. **knowledge 트랙**은 고장 없이 얻은 판단, 패턴,
합의일 때 쓴다.

위 여섯 중 실제로 존재하는 디렉터리는 `runtime-errors/`, `design-patterns/`, `workflow-issues/` 셋뿐이다.
나머지는 처음 쓸 때 만든다. 디렉터리가 없다고 다른 카테고리로 우회하지 않는다.

트랙이나 카테고리가 애매하면 **추측하지 말고** `AskUserQuestion`으로 확인한다.

## 4. 중복 확인

`docs/solutions/`를 전수 나열하고 각 문서의 `title`, `tags`, `module`을 대조한다. 문서 수가 적은
트리이므로 나열과 대조로 충분하다. 점수화나 서브에이전트는 쓰지 않는다.

**같은 문제, 같은 원인, 같은 해법**을 다루는 문서가 있으면 새 파일을 만들지 말고 **기존 문서를 갱신**한다:

- 경로와 frontmatter 구조를 유지한다
- `last_updated: YYYY-MM-DD`를 추가한다
- 본문, 예시, 참조를 새 맥락으로 보강한다
- `title`은 문제 규정이 실제로 바뀐 경우에만 고친다

같은 문제를 기술한 문서 둘은 반드시 서로 어긋난다. 그래서 갱신이 기본이다.

같은 영역이지만 각도, 원인, 해법이 다르면 새로 만들고 `## Related`에서 서로를 링크한다.

---

## 5. frontmatter

```yaml
---
title: <한국어 한 줄>
date: YYYY-MM-DD
category: <디렉터리명>        # 전체 경로가 아니라 디렉터리명만
module: <주 대상 파일이나 디렉터리>
problem_type: <위 표의 enum>
tags: [kebab-case, ...]
---
```

트랙별로 하나 추가한다:

- bug 트랙 → `symptoms:` 배열 (관측된 증상, 에러 메시지, 겉으로 보인 동작)
- knowledge 트랙 → `applies_when:` 배열 (이 지침이 걸리는 조건)

갱신할 때만 `last_updated: YYYY-MM-DD`를 더한다.

**이 목록에 없는 필드는 만들지 않는다.** `component`, `severity`, `root_cause`, `resolution_type` 같은
필드는 관리 비용만 들고 검색에 쓰이지 않는다. 그 역할은 `tags`가 한다.

**YAML 안전**: 스칼라 값이나 배열 항목에 ` #`(공백+해시, 주석으로 잘린다)이나 `: `(콜론+공백,
중첩 매핑으로 오독된다)이 들어가면 값 전체를 큰따옴표로 감싼다.

**파일명**: `<문제를-요약한-kebab-case-슬러그>.md`. 날짜 접미사를 붙이지 않는다. `date:`가 정본이다.

## 6. 본문 구조

헤딩은 한국어를 병기하고(`## 배경 (Context)`) 본문 산문은 한국어로 쓴다. 코드, 식별자, 파일 경로는
영문으로 둔다.

**문체는 `~/.claude/output-styles/korean.md`를 따른다.** 줄표(—)와 붙임표(–) 금지, 가운뎃점(·) 금지
(나열은 쉼표, 둘을 묶을 때는 "와/과"), 명사 종결 금지(개조식 불릿과 표의 칸은 예외), 번역투 금지,
연결어미 뒤 쉼표 금지. 본문은 한다체로 쓴다.

**bug 트랙**

| 섹션 | 내용 |
|---|---|
| Problem | 한두 문장으로 무엇이 잘못됐는지 |
| Symptoms | 관측된 증상. 에러 메시지, 겉으로 보인 동작 |
| What Didn't Work | 실패한 시도와 **왜** 실패했는지. 근거가 없으면 이 섹션을 생략한다 |
| Solution | 실제 수정. 필요하면 before/after 코드 |
| Why This Works | 근본 원인과 이 수정이 그것을 어떻게 해결하는지 |
| Prevention | 재발을 막는 방법. 테스트, 린트 규칙, 설정, 규약 |

**knowledge 트랙**

| 섹션 | 내용 |
|---|---|
| Context | 어떤 상황, 간극, 마찰이 이 지침을 낳았는지 |
| Guidance | 실제 지침, 패턴, 권고 |
| Why This Matters | 따르거나 따르지 않았을 때의 결과 |
| When to Apply | 이 지침이 걸리는 조건 |
| Examples | 구체적인 before/after 또는 사용 예 |

두 트랙 모두 마지막에 **`## Related`**를 둔다. 겹치는 기존 문서가 있으면 링크하고 관계를 한 줄로
밝힌다. 없으면 없다고 적는다(그것도 정보다).

### 근거 규칙

코드가 **어떻게 동작하는지** 주장할 때(enum 값, 기본값, 한계, 의미론, 실행 순서)는 정의하는 줄을
트리에서 읽고 `file:line`을 인용한다. 확인할 수 없는 주장은 단정하지 말고 완화하거나 출처를 밝힌다
("이번 세션의 결론에 따르면…").

세션 요약의 잘못된 의미가 영구 지식으로 굳는 사태가 여기서 막아야 할 실패다. 문서는 앞으로 신뢰받을
물건이므로 쓰기 전에 확인하는 편이 나중에 고치기보다 싸다.

---

## 7. 커밋

`docs/solutions/`는 git-tracked다. 문서를 쓰거나 갱신했으면 커밋한다.

`rules/git-workflow.md`의 한국어 포맷을 따른다. 타입은 `docs:`이고 본문은 WHY 중심 불릿이다.
회고 문서만 스테이징한다. 작업 브랜치의 다른 변경을 끌어들이지 않는다.

---

## 하지 않는 것

- **세션 로그(`~/.claude/projects/.../*.jsonl`) 파싱.** `/clear` 뒤의 복구 경로는 브랜치 증거 모드가 맡는다
- **`CONCEPTS.md` 어휘 수집**
- **기존 문서 일괄 갱신.** 중복으로 걸린 문서 하나만 갱신한다
- **서브에이전트 dispatch.** 이 스킬은 단일 패스다
- **한 실행에 학습 여러 건**
- **다른 스킬 호출.** 이 스킬은 파이프라인의 끝이다
