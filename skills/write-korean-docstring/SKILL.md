# write-korean-docstring

Python 코드에 한국어 docstring을 쓰는 절차와 기준이다. 목표는 IDE 툴팁에서 docstring만 읽고도 그 이름을 바르게 쓸 수 있게 하는 것이다. 막으려는 실패는 두 가지다.

- **시그니처 되풀이**: "status_code: 응답 상태 코드입니다."처럼 이름을 문장으로 바꿨을 뿐인 줄. 읽는 사람이 얻는 정보가 없다
- **바깥 참조**: "규칙 전체는 docs/api.md 4장에 있습니다."처럼 다른 파일로 보내는 문장. 툴팁에서는 그 파일을 열 수 없다

## 기본 형식

아래 형식을 묻지 않고 쓴다. 저장소에 다른 관례(NumPy 형식, 영어 docstring, pydocstyle이나 ruff `D` 규칙 설정)가 이미 있으면 그 관례를 따를지 이 형식을 쓸지 절차 2에서 묻는다.

- **문체**: 습니다체. Args 항목과 목록 항목도 습니다체 문장으로 쓴다. 이름과 이름을 잇기만 하는 대응 목록(`- RUN_START, RUN_END: agent_run()`)은 그대로 둔다
- **섹션**: Google 형식에 영어 라벨(`Args:`, `Returns:`, `Yields:`, `Raises:`, `Attributes:`, `Example:`). 컨텍스트 매니저와 생성기는 `Returns:` 대신 `Yields:`를 쓴다. dataclass와 공개 속성이 있는 클래스는 클래스 docstring에 `Attributes:`를 둔다
- **완결성**: 동작 규칙, 예외 조건, 기본값의 뜻을 docstring 안에 적는다. 같은 패키지의 다른 공개 이름을 언급하는 것은 괜찮다. 다만 그 이름의 docstring을 읽어야 이해되는 문장은 규칙을 그 자리에 풀어 쓴다
- **식별자**: 백틱 없이 쓴다(run_end, LogConfig.level)
- **첫 줄**: 요약 한 줄. 줄 폭을 넘으면 문장을 줄인다
- **줄 폭**: 한글을 두 칸으로 세어 프로젝트 줄 길이(`ruff`의 `line-length`, 없으면 79) 안에 맞춘다
- **예시**: 호출 순서나 조합을 보여야 하는 공개 API에만 넣는다(초기화 함수, 컨텍스트 매니저, 콜백 등록, 미들웨어 연결). `Example:` 아래 한 문장으로 상황을 밝히고 `::`로 끝낸 뒤 코드 블록을 둔다. doctest로 실행하지 않는다. 코드는 저장소 문서나 예제에 있는 사용 예에서 가져오고 줄이거나 바꿨으면 보고에 적는다
- **`#` 주석**: 범위 밖이다. 주석의 문체가 달라도 고치지 않는다

## 내용 기준

- **인자 한 줄마다 사실 하나 이상**: 그 값이 어디에 기록되는지, 어떤 제약이 있는지, None이면 어떻게 되는지를 적는다. 더할 사실이 없는 인자는 줄을 뺀다
  - `content: 메시지 원문입니다.` → 줄을 빼고 본문에 "content는 자르지 않고 그대로 남깁니다"를 적는다
  - `media_type: 응답의 미디어 타입입니다.` → `media_type: 응답의 미디어 타입입니다(예: "text/event-stream"). 넘기면 Content-Type 헤더가 붙습니다.`
- **동작은 결과 목록으로**: 끝나는 방식에 따라 결과가 갈리면(성공, 실패, 취소) 경우마다 목록 항목 하나로 쓴다
- **이유 한 문장**: 사용자가 의아해할 동작(예외를 내지 않음, 값을 자르지 않음, 두 번째 호출을 무시함)에는 이유를 붙인다. 이유는 코드 주석, ADR, 설계 문서에서 가져온다
- **근거는 코드**: 문서에서 가져온 내용도 코드에서 확인한다. 문서와 코드가 다르면 docstring은 코드를 따르고, 다른 점은 보고만 한다. 문서는 고치지 않는다
- **범위**: 공개 API 전부(`__all__`, 그리고 프로젝트 문서가 공개 사용법으로 설명하는 이름)와 이미 docstring이 있는 내부 이름의 문체 통일. docstring이 없는 내부 헬퍼에는 새로 쓰지 않는다

## 절차

### 1. 파악

아래를 읽고 두 목록을 만든다.

- 패키지의 `__all__`, API 문서와 사용 가이드, 예제 코드
- `pyproject.toml`의 ruff 설정(`line-length`, `D` 규칙)
- 기존 docstring의 형식과 문체

만들 목록은 두 가지다. 하나는 docstring을 쓸 공개 이름의 목록이고, 다른 하나는 예시를 넣을 이름의 후보 목록이다.

### 2. 인터뷰

기본 형식은 한 줄로 밝히고 넘어간다. 아래처럼 저장소마다 답이 다른 것만 묻는다.

- `__all__`에는 없지만 문서가 공개 사용법으로 설명하는 이름을 공개로 다룰지
- 프레임워크가 부르는 공개 클래스 멤버(콜백, 훅)에 메서드마다 쓸지, 클래스 docstring에 모을지
- 예시 후보 목록이 맞는지
- 저장소 관례와 기본 형식이 충돌하면 어느 쪽을 따를지

### 3. 샘플

기본 브랜치에 있으면 `docs/docstrings` 같은 브랜치를 먼저 만든다. 그다음 함수, 클래스, 속성, 예시가 모두 들어가는 대표 파일 하나에만 docstring을 쓰고 사용자에게 보여 준다. 분량, 완결성, 문체를 이 샘플로 확인받은 뒤에 나머지로 넘어간다. 사용자가 고친 기준은 이후 모든 파일에 적용한다.

### 4. 적용

docstring은 `scripts/render_docstring.py`로 넣는다. 문단을 한 줄로 쓰면 이 스크립트가 한글 폭 기준으로 줄을 바꾸고 목록과 섹션 항목에 걸린 들여쓰기를 붙인다. 입력 규칙은 스크립트 첫머리에 있다.

- 편집 스크립트를 scratchpad에 두고 파일마다 `apply(path, [(old, new), ...])`를 부른다. `apply()`는 대상 문자열이 정확히 한 번 나와야 그 파일을 쓴다
- 검토하다 고칠 곳이 생기면 소스를 직접 고치지 않는다. 편집 스크립트를 고치고 원래 파일로 되돌린 다음(`git checkout -- <패키지>`) 다시 돌린다. 줄 바꿈이 다시 계산되므로 폭이 어긋나지 않는다. 되돌리기 전에 그 파일들에 이번 작업 말고 다른 변경이 없는지 `git diff`로 확인한다

### 5. 검증

아래 셋을 모두 통과해야 다음 단계로 넘어간다.

```bash
python3 <스킬 디렉터리>/scripts/verify_docstrings.py <패키지> --base <작업 전 커밋> --width <줄 길이> --dump <scratchpad>/docstrings.md
python3 ~/.claude/skills/write-korean-doc/scripts/check.py <scratchpad>/docstrings.md
```

- `verify_docstrings.py`는 docstring을 뺀 AST를 base와 비교해 코드가 바뀌지 않았는지 확인한다. 그 밖에 줄 폭, 첫 줄 요약, 예시 코드 컴파일, 한다체 종결, 개조식 종결, 바깥 참조를 확인한다. 문제는 모두 0건이어야 한다
- `check.py`가 낸 연결어미 뒤 쉼표 후보는 하나씩 판정한다. 주어가 바뀌고 두 절이 모두 길 때만 쉼표를 남긴다. 나머지 쉼표는 지우거나 문장을 나눈다. 음절 오타 목록은 끝까지 읽는다
- 프로젝트의 lint, 타입 검사, 테스트를 돌린다

### 6. 통독

`docstrings.md`를 처음부터 끝까지 읽는다. 스크립트가 잡지 못하는 아래 항목을 찾는다.

- 시그니처를 되풀이하는 인자 줄
- 명사로 끝나는 목록 항목(`- method: HTTP 메서드`)
- 한 docstring 안에서 같은 낱말이나 문형의 반복("보므로 ... 봅니다")
- 지어낸 비유와 사람처럼 움직이는 사물("함수가 입력을 삼킵니다")
- 확인하지 않은 사실

고칠 곳이 있으면 4단계 방식으로 고치고 5단계를 다시 돌린다.

### 7. 보고

결과를 먼저 적고 아래를 잇는다.

- docstring을 쓴 이름의 수와 예시를 넣은 이름
- 문서와 코드가 달랐던 곳
- 남긴 쉼표와 그 이유
- 저장소 문서에서 가져오지 않았거나 줄인 예시
- 후속 결정: docstring이 문서 내용을 반복하므로 문서 동기화 규칙(예: CODING_STANDARDS)에 docstring을 넣을지 정해야 한다. 프로젝트에 `TODO.md`가 있으면 항목으로 남긴다

커밋은 사용자가 요청할 때만 한다.
